# 案例库（路由正确性的参照）

四条真实做过的片子。`scripts/route.py --test` 复现下表的路由结果。

## 案例 1：信息流卡片 demo（15s / 1920×1080）

镜头：大字提问 → 双栏对比 74:74 → 柱状 55–76 生长 → 三列要点。
全部 `cut / ui / text_heavy`，`layout_precise=false` → **4 个镜头全走 shotcraft**。
结果：450 帧，一次过，全程只改卡内文案与配色。

## 案例 2：BNB 价格曲线复刻（15s / 16:9，参考片是手机录屏）

参考片实测：笔尖沿曲线行进、身后留暗线、画完整条爆亮、随后回落并出现逐点星芒。
`follow + grow + data` → **hyperframes**（整条曲线是一条 GSAP 时间轴，笔尖跟随即相机偏移；卡库没有跟拍卡）。
结果：运动机制可复刻约 80%，整体观感约 65%。卡在笔触材质、AE 级镜头光斑、星云流动 —— 属"光效"而非"运动逻辑"。shotcraft 的卡库无此类镜头，硬套会退化成"完整曲线 + 光闪"，被否。

## 案例 3：AI 测评竖屏复刻（30s / 1080×1920）

七个镜头全是 `cut / ui / layout_precise=true` → **shotcraft 现成卡**。
做法是先在 124 张里挑构图最接近的同族卡（榜单→榜单卡、对比→天平卡、名次→领奖台卡），只改卡内文案、数字与配色，再按参考片微调间距字号；不再为复刻片新写组件。这条片之所以以前会被判成"需要自写"，是因为当时把"构图对不上"当成了引擎问题，其实它只是选卡问题。
教训：**参考片其实是 1.37:1（接近 4:3），不是竖屏**。先量画幅这一步错了，整套坐标要重算。真人用圆形"口播位"占位，原片角色美术用同语言抽象替代。

## 案例 4：三库横向实测

- shotcraft：36.2s / 1085 帧 / 19MB，`midnight` 主题，信息流蒙太奇
- iart light tier：10s / 300 帧，Canvas `draw(t)` 单画面数据片
- hyperframes：10.6s / 318 帧，HTML+GSAP 片头（踩了 CDN 与低内存两个坑）

三支片各 1 个镜头，分别 `cut+ui`、`data+loop`、`scene+long` → 路由分别给 shotcraft、iart、hyperframes，与实际选择一致。

## 结论（给路由用的经验值）

1. 只要出现"镜头跟着某个运动体走"，不要试卡库，直接交给 hyperframes 的连续时间轴。
2. `layout_precise=true` 的复刻片仍然是选卡问题：挑同族最接近的一张，改卡内文案与间距；整页版式都套不上才交 hyperframes 重排。
3. iart 适合"一张图"，超过 2 个镜头就拆出来交给别层。
4. hyperframes 只在片头/片尾独立成段时用，混进主时间轴会带进色差。

## 案例 5：引擎 A/B 实测（2026-11，1080p / 90 帧 / 2 核 4GB）

同一台机器，三种引擎各跑 90 帧，测"渲染同样的数据画面谁更快"：

| 跑法 | 耗时 | 含编码 | 结果 |
|---|---|---|---|
| shotcraft / Remotion `--concurrency=2` | 33.7s | 是 | 成功，265.9 kB |
| hyperframes（自建 seek + 本地 GSAP） | 21.2s | 否 | 成功，需先补齐 `assets/gsap.min.js` |
| iart（`?t=` 每帧重载） | 55.2s | 否 | 成功，但最慢 |
| Remotion 官方默认命令 | 11.5s 后失败 | — | `value set: 4` 超过 2 核，0 帧 |

另有字幕维度：`remotion-captions` 依赖 `remotion elements use`，本工程 CLI 无此子命令，安装即失败 → 不接入。

**结论**：以前以为"iart 比 Remotion 快"，实测相反（`?t=` 每帧重载是主因）。速度不再是选 iart 的理由；它只保留"可独立分发的单 HTML"这一条价值。hyperframes 修好后最快，但修复成本高（本地 GSAP + 自建 seek），只在复用网页时值得。
